# AniMCP Codebase Guide

This guide explains how AniMCP is assembled, where behavior lives, and a practical order for reading the code.

## What This Application Is

AniMCP is a client-side SvelteKit motion-graphics editor. Projects are edited in the browser, saved to IndexedDB, and optionally exposed to browser agents through WebMCP.

The important architectural constraint is that the UI and WebMCP share one state and mutation pipeline:

```text
UI event or WebMCP call
  -> MotionSession
  -> command transaction
  -> validated Project
  -> history + IndexedDB save
  -> reactive UI update
```

There is no account system, cloud project storage, or server-side agent executor.

## Start Here

Read these files in order:

1. [`PRODUCT.md`](PRODUCT.md) describes the product boundaries and intended user.
2. [`src/routes/motion/[id]/+page.svelte`](src/routes/motion/[id]/+page.svelte) mounts the editor route.
3. [`src/lib/features/motion/components/MotionEditor.svelte`](src/lib/features/motion/components/MotionEditor.svelte) coordinates editor startup and the major UI regions.
4. [`src/lib/features/motion/model.ts`](src/lib/features/motion/model.ts) defines the canonical project data and validation rules.
5. [`src/lib/features/motion/session.svelte.ts`](src/lib/features/motion/session.svelte.ts) owns reactive editor state, history, and persistence scheduling.
6. [`src/lib/features/motion/commands.ts`](src/lib/features/motion/commands.ts) shows how every mutation enters an atomic transaction.
7. [`src/lib/features/motion/render.ts`](src/lib/features/motion/render.ts) turns project data into visible SVG.
8. [`src/lib/features/motion/webmcp.ts`](src/lib/features/motion/webmcp.ts) exposes the same editor to browser agents.

That sequence covers the normal path from route to state to mutation to rendering.

## Repository Map

```text
src/

  lib/components/ui/              Reusable low-level controls
```

Do not edit `.svelte-kit/`. It is generated by SvelteKit.

## Routes And Startup

[`src/routes/+layout.ts`](src/routes/+layout.ts) disables server-side rendering, so the application runs as a browser client.

The main routes are:

- `/` is the landing page in [`src/routes/+page.svelte`](src/routes/+page.svelte).
- `/projects` mounts the local project library from [`MotionLibrary.svelte`](src/lib/features/motion/components/MotionLibrary.svelte).
- `/motion/[id]` mounts [`MotionEditor.svelte`](src/lib/features/motion/components/MotionEditor.svelte).
- `/api/fonts` proxies Google Fonts catalog metadata.
- `/healthz`, `/readyz`, and `/api/v1/version` are deployment endpoints.

`MotionEditor` recognizes normal saved project IDs as well as `new`, `demo`, and `template-*`. It creates or loads a project, constructs `MotionSession`, registers WebMCP tools, starts playback, and loads project fonts. Its cleanup reverses those resources and flushes pending saves.

## The Active Data Model

The current editor uses the v2 model in [`src/lib/features/motion/model.ts`](src/lib/features/motion/model.ts). A `Project` contains composition settings, a flat layer array, embedded assets, and a revision.

Layers form a hierarchy through `parentId`; they are not nested objects. Each layer owns property tracks, and each track has a default value plus ordered keyframes.

Important invariants:

- `validateProject` is the canonical contract for valid project data.
- Layer array order is back-to-front; panels display siblings in reverse order.
- Keyframes on one track have unique frames and remain frame-sorted.
- Easing is stored on the starting keyframe of a segment.
- Assets are embedded as data URLs inside the project.
- Path geometry is static in v2; its transforms and draw range can animate.
- All layer, asset, gradient-stop, and keyframe IDs must be unique.

The pure layer-panel ordering logic lives in [`layer-tree.ts`](src/lib/features/motion/layer-tree.ts).

## State And Mutations

[`MotionSession`](src/lib/features/motion/session.svelte.ts) is the state owner shared by all editor components. It separates:

- Persisted state: `project`.
- Ephemeral state: selection, playhead, previews, playback, errors, and panel status.
- History state: undo and redo snapshots.

Use `session.run` for one command and `session.commit` for an atomic group. Do not mutate `session.project` directly.

The command code is split by responsibility:

- [`commands.ts`](src/lib/features/motion/commands.ts) is the public facade and transaction boundary.
- [`command-core.ts`](src/lib/features/motion/command-core.ts) contains shared command types, selection helpers, track operations, and lock enforcement.
- [`layer-commands.ts`](src/lib/features/motion/layer-commands.ts) handles project, layer, property, paint, and asset operations.
- [`timing-commands.ts`](src/lib/features/motion/timing-commands.ts) handles keyframes, easing, timing, sequencing, copying, and motion transforms.
- [`editing.ts`](src/lib/features/motion/editing.ts) translates interactive property edits into commands, including auto-key behavior.

A transaction clones the project, applies each operation, sorts keys, checks locks, and validates after every operation. Only after the entire batch succeeds does it increment the revision. This makes a failed batch atomic, but also means an intermediate operation may not temporarily create invalid data for a later operation to repair.

## Rendering And Stage Geometry

[`render.ts`](src/lib/features/motion/render.ts) evaluates layers at a frame and produces SVG fragments. It also owns group transform semantics and SVG escaping.

[`MotionStage.svelte`](src/lib/features/motion/components/MotionStage.svelte) keeps DOM-dependent interaction logic: pointer capture, coordinate conversion, panning, selection, drag commits, and SVG overlays.

Pure stage algorithms are kept outside the component:

- [`stage-geometry.ts`](src/lib/features/motion/stage-geometry.ts) handles rotated points, local coordinates, layer bounds, group bounds, and intersection tests.
- [`stage-path.ts`](src/lib/features/motion/stage-path.ts) handles pen anchors, path serialization, path normalization, and Bezier control editing.

Long pointer gestures capture the project revision when they begin and check it when committing. Preserve that behavior so a concurrent edit cannot be silently overwritten.

## Editor Components

[`MotionEditor.svelte`](src/lib/features/motion/components/MotionEditor.svelte) composes four main surfaces:

- [`LayerPanel.svelte`](src/lib/features/motion/components/LayerPanel.svelte): layer hierarchy, activity, and composition settings.
- [`MotionStage.svelte`](src/lib/features/motion/components/MotionStage.svelte): canvas rendering and direct manipulation.
- [`MotionTimeline.svelte`](src/lib/features/motion/components/MotionTimeline.svelte): timeline rows, selection, scrubbing, and keyframe movement.
- [`MotionInspector.svelte`](src/lib/features/motion/components/MotionInspector.svelte): selected-layer and selected-segment properties.

Focused child components keep those surfaces navigable:

- [`TimelineTransport.svelte`](src/lib/features/motion/components/TimelineTransport.svelte) owns playback, timecode, auto-key, view, and zoom controls.
- [`TypographySection.svelte`](src/lib/features/motion/components/TypographySection.svelte) owns text-layer controls.
- [`FillStrokeSection.svelte`](src/lib/features/motion/components/FillStrokeSection.svelte) owns paint, gradients, and stroke controls.
- [`PropertyField.svelte`](src/lib/features/motion/components/PropertyField.svelte) connects property inputs to shared edit semantics.
- [`NumericInput.svelte`](src/lib/features/motion/components/NumericInput.svelte) separates drag previews from committed numeric edits.
- [`EasingInspector.svelte`](src/lib/features/motion/components/EasingInspector.svelte) edits selected animation segments.
- [`GradientHandles.svelte`](src/lib/features/motion/components/GradientHandles.svelte) maps stage dragging to normalized gradient coordinates.

Keep interaction state near the component that owns the pointer or keyboard lifecycle. Extract pure calculations freely, but avoid moving half of a gesture across component boundaries.

## WebMCP

WebMCP is a browser document capability, not an HTTP endpoint.

- [`webmcp-schema.ts`](src/lib/features/motion/webmcp-schema.ts) declares grouped tool and operation schemas.
- [`webmcp-runtime.ts`](src/lib/features/motion/webmcp-runtime.ts) handles validation, revisions, retries, and command commits.
- `webmcp-read.ts` and the `webmcp-*.ts` domain files register read, layer, path, animation, timeline, and atomic edit tools with `document.modelContext`.
- [`WebMcpToolCatalog.svelte`](src/lib/features/motion/components/WebMcpToolCatalog.svelte) displays the available tools in the UI.

Agent mutations use `MotionSession.commit`, exactly like human edits. `expectedRevision` protects project state, while `expectedContextRevision` protects selection-based requests. Keep those checks distinct.

## Persistence, Import, And Export

- [`storage.ts`](src/lib/features/motion/storage.ts) validates and stores projects in IndexedDB.
- [`assets.ts`](src/lib/features/motion/assets.ts) validates and sanitizes imported SVG and PNG artwork. Treat it as a security boundary.
- [`project-files.ts`](src/lib/features/motion/project-files.ts) coordinates native JSON, artwork import, SVG, Lottie, and MP4 exports.
- [`lottie.ts`](src/lib/features/motion/lottie.ts) builds Lottie documents.
- [`rasterize.ts`](src/lib/features/motion/rasterize.ts) provides raster fallbacks for export.
- [`fonts.ts`](src/lib/features/motion/fonts.ts) loads and deduplicates Google Font requests.

Native `.animcp.json` export is the only format that preserves all editable project data.

## Legacy V1 Code

The current editor does not use `src/lib/features/animation` as its working model. That directory contains the strict v1 vector format retained for validation, export compatibility, and migration.

[`migrate.ts`](src/lib/features/motion/migrate.ts) converts accepted v1 projects into v2 projects. Do not merge the v1 and v2 validators or interpolation rules merely because their names overlap; their frame and geometry semantics differ.

## Where To Make Common Changes

| Goal                            | Start here                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------- |
| Add or change project data      | `motion/model.ts`, then storage/import tests                                  |
| Add a mutation                  | the relevant command-family file, then `commands.ts` only if dispatch changes |
| Change auto-key behavior        | `motion/editing.ts`                                                           |
| Change canvas interaction       | `MotionStage.svelte`; put pure math in `stage-geometry.ts` or `stage-path.ts` |
| Change timeline interaction     | `MotionTimeline.svelte`                                                       |
| Change playback/zoom controls   | `TimelineTransport.svelte`                                                    |
| Add inspector controls          | a focused inspector section plus `PropertyField.svelte`                       |
| Change visual SVG output        | `motion/render.ts`                                                            |
| Add an agent tool               | `webmcp-schema.ts` and `webmcp.ts`                                            |
| Change local persistence        | `motion/storage.ts`                                                           |
| Change untrusted asset handling | `motion/assets.ts` and security-focused tests                                 |
| Change export behavior          | `project-files.ts`, `lottie.ts`, or `rasterize.ts`                            |

## Tests And Local Commands

```bash
pnpm dev       # local development server
pnpm test      # Vitest suite
pnpm check     # Svelte and TypeScript diagnostics
pnpm lint      # Prettier check and ESLint
pnpm build     # production build
```

The most useful test entry points are:

- [`tests/motion-core.test.ts`](tests/motion-core.test.ts): v2 model, commands, locks, paths, rendering, and groups.
- [`tests/motion-editing.test.ts`](tests/motion-editing.test.ts): interactive editing and key movement helpers.
- [`tests/motion-webmcp.test.ts`](tests/motion-webmcp.test.ts): tool registration, validation, revisions, and retries.
- [`tests/motion-stage-geometry.test.ts`](tests/motion-stage-geometry.test.ts): extracted path and stage geometry.
- [`tests/layer-tree.test.ts`](tests/layer-tree.test.ts): hierarchy display order and collapse behavior.
- [`tests/motion-storage.test.ts`](tests/motion-storage.test.ts): IndexedDB round trips.
- [`tests/motion-export.test.ts`](tests/motion-export.test.ts): SVG and Lottie behavior.
- `tests/vector-*`: legacy v1 validation, interpolation, and export.

There is currently no browser end-to-end suite. Unit tests cover the data and command layers well, but pointer choreography, browser downloads, MediaRecorder, and real font loading still require manual verification.

## Rules Worth Keeping Visible

- Route all project changes through commands and `MotionSession`.
- Validate data at persistence and import boundaries.
- Preserve revision checks around asynchronous work and long gestures.
- Never weaken SVG/PNG sanitization to make an import pass.
- Keep previews ephemeral; they must not enter project saves or history.
- Remember that panel order is the reverse of stored sibling order.
- Preserve lock checks after every individual operation in a batch.
- Keep v1 compatibility code separate from the active v2 editor.
- Prefer a focused component or pure helper over another large block in an existing editor surface.
