# WebMCP Animation Editor — Project Plan

**Status:** Hackathon build with production-grade foundations  
**Working name:** TBD  
**Date:** 2026-08-27  
**Primary relationship:** Companion/adjacent project to `draw_mind`

---

## 1. Product Summary

Build an **agent-native 2D animation editor** that lets a user and an AI agent manipulate the same visual project.

The AI agent (ChatGPT/Codex) provides the intelligence. The web app provides the creative environment and exposes its capabilities through **WebMCP**.

A representative interaction:

1. User asks ChatGPT/Codex to create an illustration.
2. The agent generates a PNG using its own image-generation capability.
3. The agent sends the image into the open editor through a WebMCP asset-import tool.
4. The editor reconstructs and stores the asset locally.
5. The asset may be vectorized in-browser.
6. The agent creates layers, keyframes, easing, transforms, and path-reveal animation through WebMCP tools.
7. The user sees the result on a normal visual canvas and timeline.
8. The user can manually edit the timeline.
9. The agent can then continue editing the exact same project state.

The project is **not** an AI chat app with an animation editor attached. ChatGPT/Codex is already the agent interface. The website is the shared tool surface.

---

## 2. Core Product Principle

> WebMCP controls the editor; WebMCP is not the editor.

The user must always have a normal animation UI:

- canvas
- layers
- timeline
- playhead
- keyframes
- property editing
- playback
- import/export

The AI uses structured WebMCP tools that execute the same commands the human UI uses.

### Required state flow

```text
                     Project Store
                          ▲
                          │
                  Project Commands
                    ▲           ▲
                    │           │
              Human UI       WebMCP
```

There must not be separate animation logic for the agent and the user.

For example, both should eventually call something equivalent to:

```ts
projectCommands.addKeyframe(...)
projectCommands.transformLayer(...)
projectCommands.animateLayer(...)
```

This shared command boundary is one of the most important architectural decisions in the project.

## 3. Decisions Made

### 3.1 No OpenAI API usage during the judging build

The hosted application will **not call the OpenAI API** during the initial hackathon/judging phase.

Reasons:

- avoid API cost entirely
- avoid owning model billing and quotas
- avoid storing an OpenAI secret
- keep the project centered on WebMCP
- let the user's existing ChatGPT/Codex environment provide intelligence and image generation

WebMCP itself does not require an OpenAI API key. The page exposes tools to an agent through `document.modelContext`.

The current WebMCP draft exposes a `ModelContext` on `document.modelContext` and lets pages register JavaScript tools through `registerTool()`.

### 3.2 Generated images are imported from the agent

The intended judging-period path is:

```text
ChatGPT / Codex
      │
      ├── generate PNG
      │
      ▼
encode / expose generated bytes
      │
      ▼
WebMCP import tool
      │
      ▼
Browser Blob
      │
      ├── raster asset
      └── optional vectorization
```

Initial transport candidate:

```ts
import_asset({
  mimeType: "image/png",
  base64: "..."
})
```

The public abstraction must remain `import_asset`, not `import_base64_image`, because base64 is an implementation detail that may later be replaced by URLs, cloud object IDs, file handles, or another binary transport.

**This transport is a critical assumption and must be validated before the rest of the editor depends on it.** See `webmcp-image-transport-test-plan.md`.

### 3.3 No authentication during judging

The initial app has no login, signup, email verification, account dashboard, or user database.

The judge/user flow should be:

```text
open site → start creating
```

instead of:

```text
open site → register → verify → onboard → create
```

Authentication will be introduced only when it unlocks real SaaS capabilities such as:

- cloud projects
- cloud asset storage
- project sharing
- paid plans
- hosted generation
- team collaboration

### 3.4 Local-first project storage

The editor remains usable without server-side storage or generation.

Initial persistence:

- project metadata: IndexedDB
- project JSON: IndexedDB
- raster/vector assets: IndexedDB as Blob data
- temporary UI state: Zustand

Saving flow:

```text
Editor state
    │
    ├── immediate in-memory update → Zustand
    │
    └── debounced durable save → IndexedDB / Dexie
```

The local-first model prevents network latency from entering basic editing operations and gives good offline/recovery behavior.

### 3.5 Server endpoints stay inside SvelteKit

The SvelteKit app owns the small server API and operational endpoints. There is no separate Go service.

The API is not being added because GA4 requires one; normal Google Analytics web collection runs client-side.

Initial server responsibilities:

- health/readiness endpoints
- version/build metadata
- operational telemetry where server collection is useful
- a safe boundary for any small server-only capability introduced during development
- future SaaS API surface within SvelteKit

The editor must remain functional when server endpoints are unavailable, except for features explicitly implemented as server-only.

No backend responsibilities during judging:

- AI generation
- project persistence
- asset persistence
- authentication
- billing
- collaboration

### 3.6 Analytics strategy

Use two layers with different purposes.

#### Cloudflare Web Analytics

Use for:

- traffic
- page views
- real-user performance
- Core Web Vitals
- general site health

Reasons:

- easy Cloudflare integration
- privacy-first
- no need to identify individual users

Cloudflare Web Analytics currently does **not** support custom product events, so it is not sufficient by itself for understanding the animation workflow.

#### Google Analytics 4

Use for product/funnel events such as:

- `editor_opened`
- `webmcp_available`
- `webmcp_tools_registered`
- `webmcp_tool_invoked`
- `webmcp_tool_failed`
- `asset_import_started`
- `asset_import_succeeded`
- `asset_import_failed`
- `asset_vectorization_started`
- `asset_vectorization_succeeded`
- `asset_vectorization_failed`
- `layer_created`
- `keyframe_created`
- `timeline_played`
- `project_exported`

Never include these in analytics payloads:

- image bytes
- base64 strings
- prompts
- user project contents
- SVG contents
- filenames that might contain personal information
- arbitrary WebMCP tool arguments

Analytics should describe **what happened**, not capture the user's creative content.

If GA4 is enabled in jurisdictions where consent is required, implement a proper consent choice and Google Consent Mode rather than silently collecting behavioral data.

### 3.7 Open source from the beginning

The editor will be open source.

Open source does not prevent a later hosted SaaS business.

Long-term model:

```text
OPEN-SOURCE / LOCAL CORE
------------------------
WebMCP
animation engine
timeline
vectorization
local projects
import/export

HOSTED SAAS
-----------
everything above
+
auth
cloud sync
cloud assets
share links
history
teams
hosted generation / credits
collaboration
```

The SaaS phase should extend the editor rather than replace its core architecture.

## 4. Technology Stack

### Frontend

| Area | Choice |
|---|---|
| Language | TypeScript |
| UI framework | React |
| Build tool | Vite |
| State | Zustand |
| Runtime validation | Zod |
| Styling | Tailwind CSS or lightweight CSS modules; keep UI dependency surface small |
| Renderer | SVG DOM |
| Local persistence | IndexedDB via Dexie |
| Vectorization | VTracer compiled to WASM |
| Heavy browser work | Web Workers |
| Agent integration | WebMCP |
| Unit tests | Vitest |
| Component tests | React Testing Library |
| Browser/E2E tests | Playwright |

### Backend

| Area | Choice |
|---|---|
| Language | Go |
| HTTP stack | standard `net/http`; add `chi` only if routing complexity warrants it |
| Logging | `log/slog` structured logging |
| API format | JSON |
| Contract | versioned `/api/v1/...`; OpenAPI can be added when the surface grows |
| Containerization | Docker |
| Database | none during judging |
| Authentication | none during judging |

### Infrastructure

| Area | Choice |
|---|---|
| DNS / edge / CDN | Cloudflare |
| Frontend hosting | Cloudflare Pages for the Vite SPA |
| Frontend analytics | Cloudflare Web Analytics + GA4 product events |
| Go API hosting | normal container/server runtime, fronted by Cloudflare; do not force Go into Workers unless there is a concrete reason |
| Object storage | none during judging |
| SQL database | none during judging |

Cloudflare Workers can execute Go compiled to WebAssembly, but Go is not a first-class Workers language and forcing a normal Go API into the Workers runtime adds complexity. A standard Go HTTP service is the cleaner choice.

## 6. Animation Data Model

Do not use Lottie as the internal editing model.

Create a small project document format owned by this application.

Example:

```ts
interface Project {
  version: number;
  id: string;
  name: string;
  width: number;
  height: number;
  fps: number;
  durationMs: number;
  assets: Asset[];
  layers: Layer[];
}

interface Layer {
  id: string;
  assetId: string;
  name: string;
  tracks: {
    position?: Track<Vec2>;
    rotation?: Track<number>;
    scale?: Track<Vec2>;
    opacity?: Track<number>;
    pathProgress?: Track<number>;
  };
}

interface Track<T> {
  keyframes: Keyframe<T>[];
}

interface Keyframe<T> {
  id: string;
  timeMs: number;
  value: T;
  easing: Easing;
}
```

The format must be versioned from day one:

```json
{
  "version": 1
}
```

Future schema changes must go through explicit migrations.

## 7. MVP Animation Capabilities

Support only the properties necessary to create compelling short 2D animations:

1. position
2. rotation
3. scale
4. opacity
5. path/stroke reveal progress

Playback uses the project's timeline and keyframe interpolation.

Do not build an After Effects clone.

### Explicitly deferred

- graph editor
- complex Bézier easing editor
- skeletal rigging
- inverse kinematics
- masks
- motion blur
- nested compositions
- audio timeline
- generative video
- full vector path editor
- complex morphing
- multiplayer collaboration

## 8. SVG Rendering Decision

Use SVG DOM as the primary scene renderer.

Reasons:

- easy layer representation
- straightforward DOM transforms
- crisp vector rendering
- raster images can still be represented with `<image>`
- vector shapes can use `<path>` / `<g>`
- path reveal is straightforward
- selection/hit testing is easier than a fully custom canvas renderer
- export/debugging is simpler

Raster and vector assets can coexist.

A PNG does **not** need to be vectorized before it can be animated. Raster assets can immediately support position, scale, rotation, and opacity.

Vectorization adds capabilities such as:

- path reveal
- shape-level editing
- fill/stroke animation
- cleaner scale-independent output

## 9. Image Vectorization Pipeline

Use VTracer WASM in a browser Web Worker.

```text
PNG
 │
 ├── optional preprocessing
 │     ├── normalize alpha
 │     ├── reduce noise
 │     └── palette simplification where useful
 │
 ▼
VTracer WASM worker
 │
 ▼
SVG
 │
 ├── sanitize
 ├── simplify if necessary
 └── import into project asset model
```

Do not run vectorization on the main UI thread.

### Important limitation

Vectorization is not rigging.

Converting one generated character PNG into SVG does not automatically provide semantic parts such as:

```text
head
upper arm
forearm
hand
pencil
```

That requires segmentation/asset planning and is deferred from the hackathon MVP.

A later system can ask the agent to generate separate transparent components for riggable assets.

## 10. WebMCP Design

Use the current `document.modelContext` WebMCP surface and feature-detect it.

WebMCP tools should call the same project command layer as the UI.

### Initial tool set

Read tools:

```text
get_project
get_scene
get_selection
```

Asset tools:

```text
import_asset
vectorize_asset
remove_asset
```

Layer tools:

```text
add_layer
remove_layer
update_layer
transform_layer
```

Animation tools:

```text
animate_layer
add_keyframes
remove_keyframes
set_duration
```

Playback/navigation tools:

```text
seek
play
pause
```

Export tools:

```text
export_project
```

Avoid exposing dozens of tiny tools if one semantic operation gives the agent a better control surface.

For example, prefer:

```ts
animate_layer({
  layerId: "pencil",
  tracks: {
    position: [...],
    rotation: [...]
  }
})
```

over many individual calls when the agent already knows the intended animation.

## 11. Asset Import Contract

The public WebMCP concept is an asset import, not a base64-specific operation.

Conceptual schema:

```ts
import_asset({
  id?: string,
  name?: string,
  mimeType: "image/png",
  encoding: "base64",
  data: "..."
})
```

Implementation requirements:

- MIME allowlist
- decoded-size limit
- reject invalid base64
- verify PNG signature / browser decodability
- avoid logging asset contents
- store result as Blob
- create object URL only when needed
- revoke temporary object URLs
- persist Blob in IndexedDB
- make duplicate/retry behavior idempotent where possible

If a one-call payload is unreliable, add the chunked transport described in the test plan rather than immediately adding paid model infrastructure.

## 15. Reliability and Production-Grade Requirements

Production-grade does not mean adding every server feature immediately.

For the initial release, it means:

### Project reliability

- schema versioning
- migrations
- stable IDs
- autosave
- corrupted-data detection
- import validation
- error boundaries
- recovery from failed asset/vectorization operations

### Editor reliability

- undo/redo command history
- deterministic command behavior
- idempotent agent operations where practical
- no expensive tracing on the main thread
- cancelable long-running vectorization

### WebMCP reliability

- feature detection
- tool registration lifecycle cleanup
- strong JSON schemas
- validation before command execution
- useful structured tool results
- cancellation handling
- error categories rather than raw stack traces

### Security

- never execute arbitrary code received through WebMCP
- validate all tool arguments
- cap imported payload sizes
- validate asset MIME/signature
- no prompt/project/image contents in analytics
- CSP suitable for the deployed app
- strict production CORS on Go API

## 18. Demo Scenario

Primary demonstration:

> "Create an animation showing how a beginner should draw a confident straight line with a pencil. Make the motion faster through the middle and gently settle at the end."

Expected flow:

```text
agent generates visual asset
        ↓
imports asset through WebMCP
        ↓
asset appears in editor
        ↓
agent creates layer(s)
        ↓
agent adds animation tracks/keyframes
        ↓
user scrubs timeline
        ↓
user manually moves one keyframe
        ↓
user asks agent to make the motion symmetrical
        ↓
agent edits same project state
```

The strongest part of the demo is the **human → agent → human → agent** editing loop, not just one-shot generation.

## 21. Architectural Verdict

The selected architecture intentionally favors a **strong browser editor with a thin server**.

That is appropriate because:

- the agent already lives in ChatGPT/Codex
- WebMCP is the core integration
- animation state must respond instantly
- vectorization is naturally browser-local with WASM
- no auth/cloud persistence is currently required
- AI API cost is intentionally zero
- analytics can largely run independently of the core editor
- a Go API boundary exists for future SaaS expansion without putting the editor on a server-dependent path

The largest remaining technical risk is **agent-generated image transport into WebMCP**. It must be tested before the project assumes it works at realistic image sizes.
